# OFM File Service

## Purpose

`ofm-file-service` owns file metadata and object storage for OFM. It is the
source of truth for:

- uploaded file records
- file ownership
- object storage paths
- file lifecycle operations

The service stores the binary object in RustFS and persists the authoritative
metadata in ScyllaDB. It exposes a gRPC API for upload, lookup, and delete
operations.

The main workflow is:

1. accept one file or a batch of files
2. store the object in RustFS
3. persist the metadata in ScyllaDB
4. return the file record to the caller

If metadata persistence fails after the object is stored, the service
compensates by removing the stored object.

## Run

Local process:

```bash
cp .env.example .env
just run
```

Direct Go command:

```bash
set -a && source .env && set +a && go run ./cmd/file-service
```

Docker stack from the shared infra repo:

```bash
cd ../ofm-infra
just file-service-up
```

## Public API

The service exposes a gRPC file API shared through `ofm-common`:

- `UploadFile`
- `UploadFiles`
- `GetFile`
- `DeleteFile`

File identifiers are generated by the service and new IDs use UUIDv7.

## Architecture Notes

- `internal/domain` defines file entities, repository contracts, and storage
  contracts
- `internal/application` owns file upload, lookup, delete, and compensation
  logic
- `internal/infra/write/scylla` owns the ScyllaDB write-model repository
- `pkg/storage/rustfs` owns the RustFS bootstrap and client wrapper
- `pkg/storage/scylla` owns the ScyllaDB bootstrap and schema setup
- `internal/presentation/grpc` owns the transport adapter
- `internal/fx` wires the process together

The service should keep file metadata and object storage ownership inside the
service boundary. Other services can request file operations, but they should
not own the stored objects or the file write model.
